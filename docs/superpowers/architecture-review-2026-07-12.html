2 · Um deep module "Handoff" — hoje são 5 arquivos acoplados por uma string

Strong in-process

agent/tools.py:1003–1080 · agent/orchestrator.py:1075, 1310, 1584–1609 · buffer/processor.py:1554, 1611 · adherence.py:414 · watchdog (LIKE 'Lead encaminhado%')

Antes — o comportamento mora em 5 lugares

tools.py — emite "Lead encaminhado para ", envia cartão, desliga IA
orchestrator.py — detecta a string em 2 loops + guard que re-dispara a tool a partir do texto final; devolve sentinela None
processor.py — decodifica o None; aborta bolhas se ai_enabled caiu no meio do envio
adherence.py — telemetria handoff_without_answer
watchdog — conta handoffs casando a mesma string no SQL

Interface implícita = a constante HANDOFF_RESULT_PREFIX. Incidente real: cartão duplo (fix S1, Prof. Sebastião).

Depois — um module, uma interface

handoff (module)

interface: request_handoff(...) → HandoffOutcome · detect(result) → bool

· ordem despedida-antes-de-desligar-IA (invariante interno)

· resolve responsável antes de ai_enabled=False

· marcador persistido num formato que o watchdog consome

· detecção única — impossível disparar 2×

Orchestrator e processor consomem HandoffOutcome tipado — o sentinela None some.

Problema. "Por que este lead recebeu dois cartões de handoff?" exige segurar 5 arquivos na cabeça ao mesmo tempo; a interface real é uma string load-bearing detectada em 3 pontos que precisam se manter sincronizados na mão.

Solução. Extrair um module handoff que é o único emissor e o único detector; devolver um tipo HandoffOutcome pela interface em vez de string-prefixo + sentinela None.

  • Locality: bugs de handoff concentram num module
  • A interface vira a superfície de teste
  • Ordenação crítica vira invariante interno, não comentário
  • Watchdog para de casar string no SQL

3 · Registry de tools — colapsar as 3 estruturas paralelas de tools.py

Strong in-process

agent/tools.py (1943): TOOL_DECLARATIONS · execute_tool (16 elifs) · get_tools_for_stage · _deferred_media/_interest_marked/_quote_executed (globals)

Antes — 3 colunas sincronizadas por string + canal oculto

declarações

lista JSON-schema (~658 linhas)

executor

if/elif × 16 (~700 linhas)

allowlist por stage

dict inline

+ efeitos diferidos atravessam tool → processor via dict[conversation_id] global (bug Wander: marcador de fotos mentiroso)

Depois — 1 declaração por tool, registry deriva o resto

tool registry (module)

Tool(
  name, schema, executor,
  stages={...},
  effects: disables_ai | defers_media | ...
)

declarações Gemini, dispatch e allowlist são views geradas do registry

Mídia diferida vira campo tipado de ToolResult — o processor recebe pelo retorno, não por global.

Problema. Adicionar uma tool = editar 3 estruturas acopladas só pelo nome-string; o contrato de efeitos (desliga IA? difere mídia? cascateia em outra tool?) é invisível no call site; e o efeito real atravessa o seam execute_tool → run_agent → processor por estado global mutável.

Solução. Uma declaração Tool co-locando schema, executor, stages e efeitos; o registry gera as três views; efeitos diferidos viajam pelo valor de retorno.

  • Leverage: 1 declaração, 3 call sites servidos
  • Contrato de efeitos vira parte da interface
  • Canal global oculto eliminado — classe do bug Wander morre
  • Teste por tool sem monkeypatch de 7 símbolos

4 · Desmembrar meta_router.py e tornar o invariante do Dev Router estrutural

Strong in-process

webhook/meta_router.py (623) · dev_router/* (156, já deep)

Antes — 6 preocupações num handler de webhook

verificação de assinatura
dev-route  (invariante = ordem textual das linhas 508–544)
dedup wamid (Redis SETNX + rollback)
máquina de estados de delivery-status (~135 linhas: rank, retry 10/30/90s, broadcast, billing)
eventos de status de template
registro/merge de lead (CTWA/BSUID) + comando !resetar

Depois — handler fino, subsistemas viram modules

verify → route_raw_payload(payload) → parse → push_to_buffer

delivery_status

rank + retry + fan-out

template_events

status de HSM

lead_intake

merge CTWA/BSUID

route_raw_payload encapsula o dev-route: o handler não consegue parsear antes de rotear — o parse acontece dentro, depois do desvio.

Problema. O router é um contêiner raso de 6 preocupações que só dividem arquivo porque a Meta posta tudo na mesma URL; e o invariante crítico do CLAUDE.md ("dev-route antes do parse") é protegido apenas por ordem de statements + testes — nada estrutural impede uma edição futura de invertê-lo.

Solução. Extrair delivery-status, template-events e lead-intake como modules próprios; introduzir um único ponto de entrada que recebe o payload bruto e só expõe mensagens já parseadas depois do desvio de dev.

  • Invariante do Dev Router vira estrutura, não convenção
  • Locality: máquina de delivery-status testável isolada
  • Complexidade real, contêiner certo — nada se perde

Problema. Depois: um deep module outbound_send — classify_meta_error único + lifecycle claim/mark/recover parametrizado por tabela + render publicado como interface (campaigns para de importar _privados do broadcast).

Problema. O mesmo fato de domínio (o que é erro permanente da Meta) tem 4 classificadores sutilmente diferentes, e a máquina claim→send→track+recovery existe 3 vezes; o único reuso atual atravessa o seam por helpers privados de outro module.

Solução. Extrair o classificador (ganho imediato, baixo risco) e depois o lifecycle parametrizado por tabela; o dispatch de job_type do scheduler vira registry de handlers em vez de escada if/elif.

  • Locality: regra de erro Meta muda num lugar só
  • Acoplamento por _helper privado vira interface publicada
  • Novo job_type = 1 registro, não escada + boilerplate

Problema. O maior ímã de bugs do repo (8+ incidentes datados) são 4 estágios de recuperação empilhados inline com tool-loops semi-duplicados — o retry2 já não reconstrói o prompt após mudar_stage (assimetria documentada como "Minor #4"). Cada fix vira mais um patch no mesmo corpo de 845 linhas; a suíte de testes datada por incidente congela essa forma no lugar.

Solução. Extrair a escada como um module com os estágios declarados como dados e um único tool-loop compartilhado. Os testes de incidente existentes atravessam a mesma interface (generate mockado) — eles são a rede de segurança da refatoração, não obstáculo.

  • Um tool-loop: a assimetria do retry2 morre por construção
  • Novo estágio de recuperação = dado, não patch
  • run_agent encolhe ~400 linhas
⚠ Maior risco do relatório: é o coração da Valéria em produção. Fazer por último, com a suíte de ~300 testes verde antes e depois de cada passo.

9 · Cadência: remover a cópia SQL do invariante

Speculative deleção parcial

follow_up/cadence.py (119, deep) · follow_up_jobs_sequence_check (SQL) · follow_up/service.py · campaigns/system_cadence.py (216, espelho derivado)

Problema. A regra da cadência vive em 4 linguagens (dataclass Python, scheduler imperativo, CHECK SQL, grafo React Flow). A cópia SQL do invariante de sequência foi a causa dos 13 dias de cadência silenciosamente morta (erro 23514 engolido como warning) — ela não pega nada que build_touch_jobs consiga produzir, só divergir.

Solução. Soltar (ou afrouxar de vez) o sequence_check — cadence.py já é a fonte de verdade e o watchdog Check 6 já cobre a classe de falha. O espelho React Flow fica: é view derivada deliberada, paga por não executar.

  • Uma cópia a menos do invariante para divergir
  • Já protegido: Check 6 detecta cadência morta

Recomendação principal

Comece pelo card 1 hoje; o primeiro deepening de verdade é o 2 · Handoff

O card 1 é meia hora de trabalho, risco zero e remove uma armadilha ativa de dados errados — o deletion test já deu o veredito. Mas o deepening de maior alavancagem é o Handoff: é o comportamento com pior locality do sistema (5 arquivos, interface implícita numa string detectada em 3 pontos), já produziu incidentes reais em produção (cartão duplo S1, handoffs cegos), tem escopo delimitado — e cada um dos outros ímãs de bug (cards 3 e 8) fica mais fácil depois que o handoff tiver uma interface tipada, porque o sentinela None e o prefixo-string hoje atravessam exatamente esses modules. Os testes de incidente existentes atravessam o seam do generate, então sobrevivem à refatoração e servem de rede.

Ordem sugerida: 1 (deletar) → 2 (handoff) → 3 (tool registry) → 4 (meta_router) → 5 (provider) → 7 (classificador de erro) → 6 (repository) → 8 (escada de retry, por último) · 9 oportunista.
